# Risk Analysis - Healthcare Workforce Planning

This document tracks quality risks and how each one maps to expected behavior and automated tests: **Risk** → **Expected behavior** → **Automation**. It was started before any code existed, so the tests are planned from risks rather than from features. Every entry is updated with evidence from real test runs.

Last updated: 2026-11-01.

## Initial risk register

Severity reflects the impact on patient safety, staff wellbeing and trust in the schedule.

| Id | Risk | Severity | Expected behavior | Rule | Planned automation |
|---|---|---|---|---|---|
| R-SCH-01 | An unqualified or expired-qualification employee is assigned, for example no one with a medication permit on a night shift | Critical | The engine never assigns them and reports the shift as unfilled | BR-H01, BR-H06 | Vitest unit tests, Playwright group D |
| R-SCH-02 | A ward is left below minimum staffing without anyone noticing | Critical | The schedule shows the shortage as a hard violation and cannot be approved | BR-H06, BR-W03 | Groups D, E, F |
| R-SCH-03 | The rest period between shifts is broken, for example an evening shift followed by an early morning shift | High | The second assignment is rejected | BR-H05 | Vitest boundary tests (exactly 11 h, 10 h 59 min), group D |
| R-SCH-04 | An employee is assigned while on leave or marked unavailable | High | The assignment is rejected | BR-H02 | Groups B, D |
| R-SCH-05 | Overlapping shifts or too many weekly hours for one person | High | Rejected | BR-H03, BR-H04 | Group D, group I |
| R-TIME-01 | Night shifts across midnight or a daylight saving change are measured wrong, so rest periods and weekly hours are wrong | High | Durations use real elapsed UTC time | BR-T01, BR-T02 | Vitest tests with fixed dates around 25/10/2026 and 28/03/2027. Availability input without a UTC offset is rejected with 400, and ranges are compared as absolute instants (verified with curl on 25/10/2026) |
| R-WF-01 | A schedule is published without approval, or changed after approval | High | The API refuses the transition or the edit | BR-W01, BR-W02 | Group F |
| R-RBAC-01 | An employee reads or edits someone else's data, or a planner approves their own schedule | High | 403 for every action outside the role's permissions | BR-A01 to BR-A03 | Group G, role by endpoint matrix. The matrix is a unit test that reads the decorators of every route (`role-matrix.spec.ts`), and `scripts/rbac-smoke.sh` checks the roles against the running API. Ownership of availability (BR-A03) is enforced by `AvailabilityAccess` and covered by unit tests and the smoke test |
| R-CONS-01 | The UI and the API disagree, for example the UI hides a button but the API still allows the action | Medium | Permissions are enforced in the API, the UI only reflects them | BR-A02 | Group H |
| R-CONC-01 | Two planners edit or generate the same schedule at the same time and double-book an employee | Medium | One request wins, the other gets a conflict error | BR-H03 | Concurrency test, approach reused from Project 1. Confirmed gap (F-05 in `exploratory-testing.md`): with 10 parallel identical availability requests, 2 to 3 overlapping rows were stored in 4 of 5 rounds, because the overlap check runs before the insert. A database level exclusion constraint is planned |
| R-AUTH-01 | A deactivated employee, or one whose role was lowered, keeps the old access until the token expires | High | Access follows the account on every request | BR-A01, BR-A02 | `active-user.guard.spec.ts`, smoke test section "Account state" (found as F-04) |
| R-INPUT-01 | Bad or out of range input reaches the database and gives 500, or a date that does not exist is moved silently | Medium | Every input is validated and rejected with 400 | BR-T01 | Unit tests in `src/common`, smoke test section "Input validation", exploratory testing (F-01 to F-03) |
| R-OPT-01 | The optimizer produces a valid but unfair schedule, for example the same person always gets night shifts | Medium | Fairness is visible in the quality score | BR-S02, BR-S03 | Group E |
| R-DATA-01 | Real personal data ends up in test fixtures or logs | Medium | Test data is generated by factories with fake names, no real people | | Factory pattern (day 30/11), review of logs |

## Evidence so far

Only behavior confirmed by a real run is listed here. Each row names the run that showed it.

The authentication, role and ownership rows come from runs of the built API against PostgreSQL 16 in a scratch environment on 2026-11-01, and are repeated on the development machine with `npm run rbac-smoke`.

| Employee | A duplicate email returns 409, the email is stored in lower case | curl and a PostgreSQL unique violation on `Employee_email_key` |
| Employee qualification | Assigning to an unknown employee returns 404 | curl and a PostgreSQL foreign key violation for employee 999 |
| Availability | An overlapping range for the same employee returns 409 | curl, ranges 08:00 to 16:00 and 12:00 to 20:00 on 25/10/2026 |

| Availability | Unknown employee returns 404, a repeated delete returns 404 | curl |

| Ownership | Before the fix the smoke test failed 6 checks: an employee could delete (204) and create (201) availability for someone else and could list everyone's records | `rbac-smoke.sh` against the API before the change |

| Account state | The token of a deactivated employee is refused at once (401), and a role change applies to an existing token at once in both directions | `rbac-smoke.sh` |
| Input validation | After the fixes, the 19 requests that had given 500 or a moved date return 400, and the server logs no error | re-run of the exploratory requests |
| Concurrency | 10 parallel identical availability requests stored 2 to 3 overlapping rows in 4 of 5 rounds | exploratory testing, F-05 |
| Manual requests | All 30 requests in `apps/backend/http/api.http` return the status code written next to them | run of the request file against the API |
| Hard constraints | Every boundary of BR-H01 to BR-H07 and BR-T03 in `scheduling-engine.md` has a unit test, including real time rest and weekly hours across both daylight saving changes | 48 Vitest tests in `src/scheduling` |
| Hard constraints | 11 deliberate mistakes in the checks, such as `<` changed to `<=` for the rest period, were each caught by at least one test | mutation check by hand |
| Qualification expiry | An expired qualification was shown as valid until 03:00 Helsinki time because dates were compared in UTC. Fixed, and the new tests fail against the old code | `employees.qualification-time.spec.ts` |
| Scheduling engine | On 300 random inputs the engine never adds an assignment that breaks an employee level rule, reports exactly what the independent validation finds, never staffs a shift above its headcount, and gives the same schedule whatever the order of the input | `engine.properties.spec.ts` |
| Scheduling engine | Compared with an exhaustive search on 3746 small inputs with many requirements (499 with a complete schedule), the engine missed 10 complete schedules (2.0 %), down from 45 (9.0 %) with a fixed order. Each miss shows as BR-H06, never as a broken rule | exhaustive search, known greedy limit in `engine.spec.ts` |
| Performance | One department with 100 shifts and 50 employees is planned in 0.66 s, down from 17 s before the checks cached time zone results, with identical output on 1000 random inputs | timing run and comparison of both versions |
| Soft scores | The fairness and workload scores fall to 50 when one of two equal employees gets every night or all the work, and both are measured relative to contract hours | `soft-scores.spec.ts` |
| Soft scores | On 300 random inputs the current ranking raises fairness from 62.0 to 76.8 and workload from 69.5 to 91.6 compared with choosing by id only, while preference stays low (33.3 against 35.3), which the weights of day 18/11 must address | baseline run |
| Quality score | Ranking by the quality score raised the average quality on 300 random inputs from 75.8 to 79.0, and from 72.8 to 76.8 with 40 shifts and 12 employees, mostly through preference (33.3 to 48.9). Workload fell (91.6 to 87.1), a trade off set by the weights | before and after run |
| Quality score | The change did not cost coverage: 10 complete schedules missed out of 499, before and after, on the same 3746 inputs | exhaustive search |
| Determinism | Floating point sums made the choice between two equal candidates depend on the input order. The Gini coefficient now sorts its values, and the property test on input order covers it | `engine.properties.spec.ts`, `soft-scores.quality.spec.ts` |
| Unit tests | 212 tests pass across 35 spec files | `npm test` |
